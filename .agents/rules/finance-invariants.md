# Financial & Accounting Invariants

## 1. Absolute Monetary Integrity
- **No Floating-Point Operations**: IEEE 754 floating-point numbers (`float32`, `float64`, `number` in JS/TS) MUST NEVER be used for monetary amounts or balance calculations.
- **Fixed Precision Representation**: All monetary values MUST be stored and computed as integer minor units (e.g. cents, 100 = $1.00) or fixed-precision decimal types (`NUMERIC(20,4)` in PostgreSQL, `shopspring/decimal` in Go).

## 2. Double-Entry General Ledger Rules
- **Balanced Postings**: Every journal entry MUST consist of at least two line items (debits and credits). The total sum of debits MUST EXACTLY equal the total sum of credits before posting:
  $$\sum \text{Debits} = \sum \text{Credits}$$
- **Immutability of Posted Entries**: Once a journal entry status is changed to `POSTED`, it CANNOT be modified or deleted. Any corrections MUST be executed via a new Reversal Journal Entry or Adjustment Journal Entry.
- **Sequential Entry Numbers**: Posted entries within an organization must receive an immutable, monotonically increasing entry number.

## 3. Accounting Period Locks
- Fiscal periods can be marked as `OPEN`, `CLOSED`, or `LOCKED`.
- The posting engine MUST check the transaction date against fiscal period status. Any attempt to post an entry into a `CLOSED` or `LOCKED` period MUST be rejected with a domain error.

## 4. Idempotency & Idempotency Keys
- All financial posting endpoints, CSV imports, and external webhooks MUST accept an `Idempotency-Key` header.
- Re-submitting a payload with an existing `Idempotency-Key` MUST return the original result without re-executing ledger mutations.

## 5. Atomic Audit Logging Invariant
- Every financial mutation (creating accounts, posting entries, reversing entries, updating period status) MUST write an immutable `audit_logs` record **atomically** within the exact same PostgreSQL database transaction (`BEGIN ... COMMIT`).
- Every audit record MUST capture:
  1. `organization_id`
  2. `actor_id` (User ID mapped to OIDC subject identifier, or System Worker ID)
  3. `timestamp` (UTC ISO-8601 with microsecond precision)
  4. `correlation_id` (Trace ID)
  5. `action_type` & `delta_summary`

## 6. AI & Machine Learning Guardrails
- Predictions, categorization suggestions, and forecasts generated by AI/ML models are strictly advisory.
- AI models MUST NEVER post journal entries automatically. All AI suggestions require explicit human review and approval by an authorized user (`Accountant` or higher) before posting.
- All AI suggestions MUST output:
  1. `confidence_score` (0.00 to 1.00)
  2. `explanation_text`
  3. `model_version`
